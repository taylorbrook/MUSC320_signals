**Performance Controls -- 4 Sliders with smooth ramping:**

Each slider follows the pattern: slider (0-127) -> / 127. -> pack $1 50 -> line~ -> parameter target. This provides click-free smooth interpolation at 50ms ramp time. The slider outputs override the automation-driven line~ for that parameter when moved (the instructor takes manual control).

Slider 1 -- "Noise Speed" (LFO rate for Voice 1):
- slider -> / 127. -> * 7.9 -> + 0.1 (scale to 0.1-8.0 Hz range) -> pack $1 50 -> line~ -> cycle~ frequency inlet of Voice 1 LFO
- Default position: ~30 (out of 127), representing ~2 Hz LFO
- When moved, overrides the line~ automation for Voice 1 LFO rate

Slider 2 -- "Tone Pitch" (base frequency for Voice 2):
- slider -> / 127. -> * 320. -> + 80. (scale to 80-400 Hz range) -> pack $1 50 -> line~ -> cycle~ frequency inlet of Voice 2 carrier
- Also: same scaled value + detuning offset -> second cycle~ of Voice 2 (tracks carrier + ~2 Hz)
- Default position: ~42 (out of 127), representing ~185 Hz

Slider 3 -- "Noise/Tone Mix" (balance between noise voice and tonal voices):
- slider -> / 127. -> voice 1 amplitude *~ (noise level)
- slider -> / 127. -> expr (1. - $f1) -> voices 2+3 amplitude *~ (tone level)
- Uses pack $1 50 -> line~ for each path for smooth ramping
- Default position: ~64 (center, equal mix)
- Alternatively, if expr is too complex: use two separate scaling paths. One slider value goes to noise amplitude line~, the inverted value (1-x via !- 1. or * -1. + 1.) goes to tone amplitude line~. Use simpler Max objects that students know: * -1. then + 1. to invert.

Slider 4 -- "Drone Detune" (detuning amount for Voice 3):
- slider -> / 127. -> * 10. (scale to 0-10 Hz detune range) -> this value is ADDED to Voice 3 base frequency for the detuned partial's cycle~
- pack $1 50 -> line~ for smooth ramping
- Default position: ~38 (representing ~3 Hz detune)

**Important:** Each slider needs a connection path to override or supplement the automation line~ objects. The simplest approach: use SEPARATE line~ objects for slider-driven parameters (not the same line~ that receives automation messages). The slider line~ and automation line~ can both feed into the parameter target through a +~ or a gate mechanism.

RECOMMENDED APPROACH: Use the slider line~ objects as the ACTUAL parameter sources, and have the automation messages feed into those SAME line~ objects. When metro triggers a new automation message, it writes to the line~. When the instructor moves a slider, the pack $1 50 writes to the same line~, overriding the automation. This is the "hybrid automation" model: automation runs until the instructor intervenes. This is cleaner than parallel line~ objects.

To implement this: Route both the automation message AND the slider's pack output to the SAME line~ inlet. The most recent message wins (line~ behavior). Label clearly in comments which line~ objects are "automation + slider" dual-input.
