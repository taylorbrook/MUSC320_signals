  <action>
Create the directory `patches/` and write `noise-sculpture-demo.maxpat` as a valid .maxpat JSON file.

The patch must implement the following architecture. All signal (~) objects are limited to the Week 7 syllabus set: noise~, cycle~, *~, +~, line~, sig~, live.gain~, dac~. Control-rate objects (toggle, metro, message, loadbang, pack, select, slider, comment, etc.) are from students' existing Weeks 1-6 vocabulary and are freely available. clip~ is used as a safety limiter (infrastructure, not pedagogical).

**Voice 1 -- Rhythmic Noise:**
- noise~ -> *~ (amplitude gate) -> *~ 0.25 (voice level) -> to mix bus
- Amplitude gate driven by a unipolar LFO: cycle~ (frequency ~2 Hz, automated by line~) -> *~ 0.5 -> +~ 0.5 (shifts -1..1 to 0..1)
- line~ automates the LFO cycle~ frequency (slow sweeps between 0.5 and 6 Hz over the automation cycle)
- A second line~ automates the voice amplitude (swells and fades over the automation cycle)

**Voice 2 -- Tonal AM / Beating:**
- cycle~ (frequency ~185 Hz, automated by line~ for slow pitch drift) -> *~ <- cycle~ (frequency ~187 Hz, tracks main freq + small detuning offset)
- The multiplication creates beating at the difference frequency (~2 Hz) and ring modulation sidebands
- Result -> *~ (amplitude from line~) -> *~ 0.25 (voice level) -> to mix bus
- line~ automates the base frequency (slow drift between 150-250 Hz range over 15-20s cycle)
- A second line~ automates the voice amplitude

**Voice 3 -- Evolving Drone:**
- cycle~ (frequency ~110 Hz, automated by line~ for very slow pitch movement) -> output A
- cycle~ (frequency = main freq + small detune, e.g., +3 Hz) -> *~ 0.7 (partial amplitude) -> output B
- output A +~ output B -> *~ (amplitude from line~) -> *~ 0.25 (voice level) -> to mix bus
- line~ automates the drone base frequency (very slow, meditative drift between 80-150 Hz)
- A second line~ automates the drone amplitude
- The detuning creates slow beating that provides organic movement

**Mix Bus and Output Stage:**
- voice1 +~ voice2 -> +~ voice3 -> live.gain~ (stereo, default -12 dB) -> clip~ -0.9 0.9 -> dac~
- live.gain~ must have parameter_enable: 1 and parameter_initial: [-12.0]
- clip~ arguments: -0.9 and 0.9 (hard safety limiter)

**Automation Engine:**
- toggle -> select 0 1
- select outlet 1 (toggle ON): triggers "start" message chain
  - Send initial line~ values (safe starting state for all voices)
  - Start metro (interval ~15000 ms for 15-second automation cycle)
  - Metro bangs a series of message boxes containing multi-segment line~ target-time lists
  - Each voice has 2 line~ objects (one for frequency-related parameters, one for amplitude), each driven by its own multi-segment message
- select outlet 0 (toggle OFF): triggers "stop" message chain
  - Stop metro
  - Send all amplitude line~ objects to 0 with 100ms ramp: "0, 0 100"
  - This creates a smooth fade-out with no clicks

**Multi-segment line~ message design (per user decision: looping, 15-20s cycle):**
- Voice 1 LFO rate: "1.5, 4. 5000, 0.8 3000, 6. 4000, 2. 3000" (sweeps LFO rate through different speeds)
- Voice 1 amplitude: "0, 0.8 4000, 1. 3000, 0.5 5000, 0.9 3000" (swelling noise presence)
- Voice 2 frequency: "185, 220 6000, 170 5000, 200 4000" (gentle pitch drift)
- Voice 2 amplitude: "0, 0.7 3000, 1. 5000, 0.6 4000, 0.8 3000" (tonal layer fading in/out)
- Voice 3 frequency: "110, 95 7000, 130 5000, 105 3000" (very slow drone drift)
- Voice 3 amplitude: "0, 0.6 2000, 0.9 6000, 0.7 4000, 0.5 3000" (drone presence)

(These are starting values. The executor should tune them for musical quality -- the exact numbers matter less than the overall sonic character being warm, dark, and evolving.)

**JSON format requirements:**
- Root object: `{ "patcher": { ... } }`
- patcher.fileversion: 1
- patcher.appversion: { "major": 9, "minor": 1, "revision": 2, "architecture": "x64", "modernui": 1 }
- patcher.rect: [100, 100, 1200, 850]
- patcher.openinpresentation: 1
- patcher.default_fontsize: 12.0
- Every box needs: maxclass, id (unique "obj-N"), numinlets, numoutlets, outlettype, patching_rect [x, y, w, h]
- Every patchline needs: source [id, outlet], destination [id, inlet]
- Signal outlets use outlettype "signal"; control outlets use "int", "float", "bang", "" as appropriate
- *~ with a fixed multiplier: use "text" attribute set to "*~ 0.25" (or the relevant value), maxclass "newobj"
- +~ similarly: maxclass "newobj", text "+~"
- noise~, cycle~, line~, clip~, dac~: maxclass "newobj" with appropriate text
- live.gain~: maxclass "live.gain~" with parameter attributes (see research Example 8)
- toggle: maxclass "toggle"
- metro: maxclass "newobj", text "metro 15000"
- message boxes: maxclass "message", text contains the line~ multi-segment list
- select: maxclass "newobj", text "select 0 1"
- loadbang: maxclass "newobj", text "loadbang"

**ID naming convention:** Use sequential obj-1, obj-2, etc. for all objects. Keep a clear mapping in comments/notes during implementation so patchlines connect correctly.

**Important anti-patterns to avoid (from research):**
- Do NOT connect noise~ directly to dac~ at any point -- always through *~ amplitude control
- Do NOT use loadbang to auto-start DSP -- instructor controls when audio begins
- Do NOT set line~ ramps shorter than 20ms -- causes clicks
- Ensure the starting value of retriggered line~ messages begins at 0 or near the expected current value to avoid clicks at retrigger points
